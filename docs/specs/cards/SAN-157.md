# SAN-157 — Linked issues

Owner 2026-10-18: link any issue to another with a type, add from the issue view or a shortcut, list the links grouped by type in the detail (key, summary, status, priority, assignee), remove them; links show on both issues; CLI and MCP link and unlink. This card owns links for SAN-76 and SAN-94.

## Context

- No behaviour spec: SAN-155 (observing the reference) is not done and, per D56, the investigator no longer observes the reference tracker. The product agent grounds the behaviour on public knowledge of trackers (typed links: blocks / is blocked by, relates to, duplicates / is duplicated by, clones / is cloned by).
- Issue view: `web/src/widgets/issue-detail/` (description, attachments, subtasks, comments). No '+' add menu yet (SAN-159).
- Search across projects exists for the command palette and `GET /api/projects/{key}/issues?q=` per project.
- Permissions: issues live in projects; a member of one project must not learn about issues of a project they cannot see.

### Behaviour baseline (product, public knowledge)

- Every typed link has a direction and an inverse label: creating "blocks" on the source shows as "is blocked by" on the target, never the same word on both ends.
- A small set of link types is symmetric ("relates to"): creating it from either issue produces one row, shown identically on both sides.
- The same pair of issues cannot carry the same link type twice in either direction; the create action rejects or no-ops on a duplicate instead of adding a second row.
- A link always shows on both issues it connects, each from its own point of view (own label, other issue's key and summary).
- Deleting an issue removes its links; the remaining issue on the other end loses that row, it does not show a broken or orphaned reference.
- Links are visible across projects when the viewer has access to both linked issues; a link to an issue the viewer cannot see either disappears or is shown without exposing its details.
- Links in a list are grouped by type (all "blocks" together, all "relates to" together), not by creation time, so a reader scans relationship kind before chasing dates.
- Removing a link is a single action from either issue and takes effect on both ends at once, never leaving a one-sided link.

## Scope

- Data: `issue_link (id, source_issue_id, target_issue_id, link_type, created_by, created_at)`, one row per link, inverse label derived (`blocks` shown as "is blocked by" on the target). No self links, no duplicate (same pair and type, either direction for symmetric types).
- API: list links of an issue (both directions, each with the other issue's key, summary, status, priority, assignee and whether the viewer can open it), create, delete. Cross-project allowed when the caller is a member of both projects.
- Web: a "Linked issues" section in the issue view; add (type + issue picker searching by key or text); remove; links grouped by relationship.
- CLI `santi issues link KEY-1 blocks KEY-2`, `santi issues unlink …`, links shown in `santi issues show`; MCP `link_issues`, `unlink_issues`, links in `get_issue`.

Out: split into a linked copy (PB-47), link notifications, links on board cards beyond what the panel decides.

## Decisions

Panel 2026-10-21: product, ia and ux; Q3 split, ia and ux win. Architect challenge (orchestrator), D59:
- Table `issue_link (id, source_id, target_id, link_type text CHECK IN ('blocks','relates','duplicates','clones'), created_by, created_at)`, FKs `ON DELETE CASCADE`, `CHECK (source_id <> target_id)`, one unique index on `(least(source_id,target_id), greatest(...), link_type)` for every type (no mutual blocks, duplicates or clones; amended after qa), indexes on both ends.
- `GET /api/projects/{key}/issues/{number}/links` returns only links whose other end the viewer can open (member of its project, project not trashed); `POST .../links { relation, issue: "KEY-12" }` from this issue's side (`relation` one of blocks, is_blocked_by, relates, duplicates, is_duplicated_by, clones, is_cloned_by; stored normalised); `DELETE .../links/{id}`. Creating needs edit rights on this issue and membership of the other issue's project; a target the caller cannot see answers 404 (no leak).
- Board and backlog `Card` gain `blocked_by: Vec<String>` (keys of blockers not in a done category that the viewer can open), filled in the existing card query (one extra LEFT JOIN aggregate, no new statement; budgets stay).
- Issue delete removes its links (cascade); archived projects read-only like other edits; no notifications.

## States (ux)

- **Section**: "Linked issues" after Subtasks, before Comments. Empty: only the heading and a "Link issue" button render (no placeholder text) so the add path stays discoverable; archived project drops the button (read-only).
- **Groups**: one subheading per relationship with rows, fixed order — Blocks, Is blocked by, Relates to, Duplicates, Is duplicated by, Clones, Is cloned by. Groups with no rows don't render.
- **Row**: type glyph · key · summary (link, truncates, `title` = full summary) · status pill (CATEGORY tone) · priority icon · assignee avatar · remove button (icon only, `aria-label="Remove link to KEY-3"`).
- **Add row**: opens under "Link issue" (mirrors subtask's `adding` row). Native select of link type, default "blocks" (most common first move linking work). Issue picker: text input, searches key or summary across the viewer's projects, excludes the current issue and issues already linked; arrow keys move the result list, Enter picks, Escape cancels and returns focus to "Link issue". Empty results: "No issue found."
- **Saving**: submit disables the row and shows a spinner (matches subtask `move.isPending`); on success the add row closes and the new row appears in its group (new group created in the fixed order above if needed).
- **Errors**: create fails → "Could not link the issues." under the add row, picker keeps its query so the user retries without retyping. Remove fails → "Could not remove the link." inline under that row; row stays, action is retryable.
- **Loading**: skeleton rows under the heading while links fetch (same shape as the subtask list).
- **Partial data**: a linked issue the viewer can't open is omitted with no row and no count (Q3) — never a dead-end or broken-reference row.
- **Long text / many items**: summary truncates with a tooltip; groups grow with the page, no inner scroll or pagination, same as subtasks.
- **No permission**: viewer without access to the issue never sees the section.
- **Phone 375px**: row wraps to two lines (glyph/key/summary, then pill/priority/avatar/remove), each control a 44px target; the picker's result list is full width, no sideways scroll.
- **Dark theme**: status pill and priority reuse existing CATEGORY/D36 tokens; no new colors.
- **Keyboard order**: "Link issue" → type select → issue picker → result list → submit/cancel → each row's remove button in group then row order. Focus returns to "Link issue" after add/cancel, and to the next remove button (or "Link issue" if it was the last row) after a removal.
- **`L` shortcut**: opens the add row and focuses the type select; if already open, moves focus there. Listed in the shortcut sheet next to `g l`.
- **Board card marker**: icon + "Blocked" text, `title="Blocked by KEY-3, KEY-7"` listing not-done blockers; renders only when at least one blocker isn't done.

## Acceptance

- Link KEY-1 blocks KEY-2 from KEY-1 → KEY-2 shows "is blocked by KEY-1"; removing from either side removes both views; duplicates refused (422 naming `issue`), self link refused.
- A link to an issue in a project the viewer cannot open is not listed and not counted; creating one answers 404.
- Board cards and backlog rows blocked by an open issue show the Blocked marker with the blockers in the title; it disappears when the blocker reaches done.
- `L` opens the add row; every state in "States (ux)" at 1440 and 375, light and dark.
- CLI `santi issues link KEY-1 blocks KEY-2`, `unlink`, links in `santi issues show`; MCP `link_issues`, `unlink_issues`, links in `get_issue`.
- Gates: server (fmt, clippy, tests, sqlx check, perf budgets unchanged), web (typecheck, lint, format, coverage > 90 %, size budgets), qa (contract, tenancy), ux screenshots.
