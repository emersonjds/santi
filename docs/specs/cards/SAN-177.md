# SAN-177 — Active invites on the Members page, and revoke

Owner (2026-10-19): a group invite link (SAN-176) goes to a WhatsApp group, so a leaked link must
be stoppable, and the admin wants to see who joined with each link.

## Decisions

| # | Question | Winner |
|---|---|---|
| 1 | What the list shows | Live invites only: not expired and not full (`used_at IS NULL`, `expires_at > now()`). Ended, full and revoked links drop out; no "Ended" group (they cannot do anything, and the Members list already shows who is in). |
| 2 | How revoke works | Sets `expires_at = now()` on the invite. No new column: the preview and accept already answer 410 `invite-expired`, so a revoked link reads like an expired one. People who joined stay members. |
| 3 | Who | Project admins only, for both list and revoke. Another project's invite id is 404. Revoking an ended invite is 404. Archived project: list works, revoke is refused like every write (`check_writable`). |
| 4 | Joiners | Each live invite lists who joined with it (`invite_use`): name, email, joined at. Emails are already visible to admins on the Members page. |
| 5 | Accept racing a revoke | Accept checks expiry against `clock_timestamp()`, not the transaction start, so an accept that began before a revoke committed answers 410 once the revoke's 204 is out. |
| 6 | `created_at` | Stored on `invite` (migration 0025, default `now()`); rows made before it are backfilled as `expires_at - 7 days`, which held for every invite until then. |
| 7 | CLI revoke | `santi invites revoke` asks `Revoke invite {id} in {KEY}?` unless `--yes`, like `issues delete`; a "no" keeps the link (exit 10). |
| 8 | Focus after revoke | Focus moves to the next row's Revoke, else the previous row's, else the "Invite links" heading when no link is left. A failed revoke leaves focus in the dialog; Cancel returns it to the row's Revoke. |
| 9 | 404 on revoke | The row drops and the list refetches. If access to the project is gone the refetch fails and the section shows its error state (accepted). |
| 10 | Joiners who later left | Stay listed with their email for admins (accepted: they were members when they joined). |

## API

- `GET /api/projects/{key}/invites` → `[{ id, role, max_uses, uses, created_by_name, created_at, expires_at, joined: [{ user_id, name, email, joined_at }] }]`, newest first.
- `DELETE /api/projects/{key}/invites/{id}` → 204.
- OpenAPI updated; never return the token or its hash.

## Web (Members page, admins only)

- Section "Invite links" under the members list. Each row: role, "2 of 3 spots used", "expires in 5 days", "by <name>"; below it the people who joined (name, email, relative date). A "Revoke" button (44 px) opens a confirm: title "Revoke this link?", text "Nobody else can join with it. People who already joined stay in the project.", buttons "Revoke link" and "Cancel".
- After revoking, the row leaves the list and a toast says "Link revoked."
- Empty: "No active invite links." Loading skeleton and error with retry like the members list.
- Archived project: rows shown, Revoke locked like other controls.
- 375 px first: rows stack, no horizontal scroll; light and dark.

## CLI / MCP

- `santi invites <KEY>` lists live invites (id, role, spots used/total, expires, joiners); `--json` raw.
- `santi invites revoke <KEY> <id> [--yes]` (asks first, decision 7).
- MCP tools `list_invites` and `revoke_invite` (destructive hint on revoke).

## Acceptance

- Admin sees live invites with spots and joiners; members get 403, strangers 404.
- Revoke: the link then answers expired in preview and accept; joined people stay.
- Another project's invite id: 404. Ended invite: 404.
- qa review (access control).
