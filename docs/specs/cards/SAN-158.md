# SAN-158 — Attachments on issues, comments and the create form

Owner (2026-10-18/19): add files to an issue (detail, while writing a comment, while creating the
issue). Urgent: PRM work needs documents and images. Subtasks: SAN-166 storage, SAN-167 slice,
SAN-168 web (detail), SAN-175 web (comments + create form), SAN-169 CLI/MCP, SAN-170 Railway bucket.
Baseline: OR-28 (attach, delete own), OR-53 (trash with the project), OR-63 (archived is frozen) in
`docs/specs/behavior/organizations.md`. Decision log entry: D53.

## Decisions

| # | Question | Winner |
|---|---|---|
| 1 | Where they show | An "Attachments" section under the description in the issue detail (dialog and full page), title with the count ("Attachments · 3"). Comment files show under the comment text. One list per issue: the section lists every file, comment files included, each saying where it came from ("in a comment"). |
| 2 | Entry points | "Attach files" button in the section header (hidden file input, `multiple`); drag and drop anywhere on the issue detail (drop overlay "Drop files to attach"); paste an image while the detail has focus outside an editor. In a comment composer: an attach button plus drop and paste into the composer (SAN-175). In the create dialog: an attach button and drop (SAN-175). |
| 3 | Limits | 25 MB per file, 100 files per issue, 10 files per upload request. Allowed: PNG, JPEG, GIF, WebP, PDF, DOCX/XLSX/PPTX, ODT/ODS/ODP, TXT, CSV, MD, ZIP. Type decided from the bytes (magic numbers) plus the extension; text types must be valid UTF-8. SVG and HTML are refused (script carriers). |
| 4 | Who | Project members attach; the uploader or a project admin deletes (OR-28; santi has no viewer role yet). Archived project: list and download work, attach and delete are locked (OR-63). Trashed project: everything 404; purge deletes the stored objects (OR-53). |
| 5 | Storage | One storage port, two adapters, picked by env and checked at startup: S3-compatible (Railway Storage Bucket in production, MinIO/R2/S3 for self-hosters; vars `SANTI_S3_BUCKET`, `SANTI_S3_ENDPOINT`, `SANTI_S3_REGION`, `SANTI_S3_ACCESS_KEY_ID`, `SANTI_S3_SECRET_ACCESS_KEY`, path-style) or local disk (`SANTI_ATTACHMENTS_DIR`, default `./data/attachments`). Prefer the `object_store` crate (S3 + local + in-memory, presigned URLs) if it fits; architect/backend confirms. Object key `<project_id>/<issue_id>/<uuid>`, never the file name. |
| 6 | Serving | `GET …/attachments/{id}` answers: S3 → 302 to a presigned URL valid 5 min carrying `response-content-disposition` and `response-content-type`; local → streamed by the server. Images (PNG/JPEG/GIF/WebP) `inline`, everything else `attachment`; always `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox` on streamed files. When S3 is configured the SPA CSP `img-src` adds the bucket endpoint origin so previews load. No thumbnail generation: the image itself, lazy-loaded and scaled by CSS. |
| 7 | API | `POST /api/projects/{key}/issues/{number}/attachments` (multipart, field `file` repeated, optional `comment_id`), `GET …/attachments` (list), `GET …/attachments/{id}` (download), `DELETE …/attachments/{id}`. Attachment: `id, file_name, content_type, size_bytes, uploader_id, uploader_name, comment_id, created_at`. Body limit on the upload route only (10 × 25 MB + framing); streamed to storage, never the whole file in memory. Rate limit uploads per account. History entries come with the issue history log (SAN-186). |
| 8 | Comments and create form (SAN-175) | No server drafts. Create form: files are queued in the dialog and uploaded right after the issue is created; a failed file shows its error with Retry on the new issue. Comment: the comment is posted, then its files upload with `comment_id`; a failed file shows under the comment with Retry. Deleting a comment deletes its files. |
| 9 | Web links | Not in this card: a separate card later. |
| 10 | Delete | Confirm "Delete <file>? This cannot be undone."; the row goes, then the stored object is removed after the commit (best effort; a missed object is an orphan, harmless). |
| 11 | `comment_id` part (qa) | Read in chunks; more than 20 bytes or not an integer is a 422 on `comment_id`, no surrounding spaces allowed. |
| 12 | Project state at save (qa) | The insert transaction locks the project and re-checks it (`lock_project` + `check_active`) before locking the issue: archived or trashed while the body streamed answers 409 / 404 and the stored objects are deleted. |
| 13 | Files on a comment (qa) | Only the comment's author or a project admin attaches to a comment (same rule as deleting it); anyone else gets 403 and the stored objects are deleted. |
| 14 | Deleting a comment (qa) | One transaction that locks the issue row first, so a concurrent upload to the comment (which locks the same row) either lands before the keys are read or fails its foreign key afterwards. |
| 15 | Startup warnings (qa) | On Railway (`RAILWAY_ENVIRONMENT` set) with local-disk storage, and for an `http://` S3 endpoint whose host is not localhost or a loopback, private or unique-local address, the server logs a warning and still starts. A single-label host such as a compose service name also warns. |
| 16 | Oversized and slow bodies (qa) | A body past the upload limit answers 413 `payload-too-large`; a broken multipart body stays 422. The upload route has a 10-minute deadline on the whole body (`DeadlineBody`), not an idle timeout. |
| 17 | Local downloads (qa) | Served with `Content-Length` from the object size and never compressed: the compression layer skips any response carrying `Content-Disposition`. |
| 18 | File names (qa) | Every Unicode format character (category Cf, listed by hand from Unicode 15) is stripped, besides controls. A `.png` holding just the 8-byte PNG signature still passes: the signature is what is checked. |
| 19 | Secrets in logs (qa) | `S3Config`'s `Debug` prints `<redacted>` for the secret key. |
| 20 | Migration 0026 (qa, accepted) | The unique index on `issue_comment` is built without `CONCURRENTLY`: the table is small and the lock is brief. No change. |
| 21 | Upload progress (web) | Uploads use one XMLHttpRequest helper, one file per request, because fetch has no upload progress; every other call stays on openapi-fetch (D38). |

## States (web)

- Empty: section shows "No attachments yet." and the Attach button; drop overlay still works.
- Uploading: one row per file with name, size, progress bar and Cancel.
- Failed: the row stays with the reason ("Larger than 25 MB.", "This file type is not allowed.", "Upload failed. Check your connection.") and Retry / Remove.
- List: images as a grid of tiles (lazy image, name on hover/focus); other files as rows with a type icon, name, size, uploader and relative date; each with Download and (author/admin) Delete.
- Preview: clicking an image opens a lightbox (Esc closes, arrows move, swipe on touch, Download inside).
- Delete confirm as decision 10. Archived: Attach and Delete locked like other controls, Download stays.
- 375 px: tiles two per row, rows stack, 44 px targets, no horizontal scroll; light and dark.

## Acceptance

- Upload an image and a PDF to an issue; both list, the image previews, both download with the right name.
- Refused: 26 MB file, SVG, a `.png` whose bytes are HTML; the 101st file.
- A member of another project gets 404; a non-author member cannot delete; an admin can.
- Archived: download yes, upload/delete no. Trash hides; purge removes the objects.
- Comment files and create-form files land on the issue with `comment_id` / right after create.
- qa review (uploads, auth, tenant, storage) before release.
