# SAN-224 — Switch a project between Kanban and Scrum

Owner, 2026-10-28: the board type is fixed at creation. Converting Qore from Kanban to Scrum took
export → edit `board_type`/`done_window_days` → purge → restore, losing issue history, notifications
and attachments.

## Context

- Board type rules (crates/santi-server/src/boards/domain.rs): column WIP limits exist only on Kanban
  (`check_wip_limit`); `done_window_days` (hide done work after 7/14/30 days) only on Kanban
  (`check_done_window`). Scrum has sprints (active, future, closed with reports); the Scrum board shows
  the active sprint; the backlog lists sprints then the backlog. Kanban has no sprints and a board of
  all open work.
- Project settings has a "General" section (SAN-225) with name and key, admin only.
- No behaviour spec covers converting a board (docs/specs/behavior has none). Deviation from the
  card flow: no `investigator` run (cost); the panel grounds votes in public documentation of other
  trackers. Owner may ask for an investigator pass later.

## Scope

- Admins switch the board type from project settings, the CLI (`santi projects edit --type`) and
  MCP (`update_project` `board_type`). Issues, comments, attachments, links, history and keys stay.
- Kanban → Scrum: WIP limits and `done_window_days` are cleared; open issues go to the backlog (the
  Scrum board shows only the active sprint, and there is none yet).
- Scrum → Kanban: what happens to the active sprint, future sprints and closed sprints (reports) is
  the panel's decision; the confirmation says it before switching.
- The change is recorded in the project history when SAN-186 lands.

## Open questions (panel)

| # | Question | Options |
|---|---|---|
| 1 | Where | (a) a "Board type" control in the General section; (b) a row in the Danger zone; (c) both |
| 2 | Scrum → Kanban with an active or future sprints | (a) refuse until no sprint is active or planned ("Complete the active sprint and empty future sprints first"); (b) complete the active sprint automatically (open work stays on the board) and dissolve future sprints into the board; (c) switch and keep sprints hidden, coming back if switched to Scrum again |
| 3 | Closed sprints and reports after Scrum → Kanban | (a) kept, reports stay reachable from Reports; (b) kept but hidden until switched back; (c) deleted |
| 4 | Kanban → Scrum with WIP limits / done window set | (a) cleared silently and said in the confirmation; (b) refuse until cleared |
| 5 | Confirmation | (a) dialog listing exactly what changes (counts: open issues to backlog, limits cleared, sprints affected) with "Switch to Scrum/Kanban" button; (b) inline note + Save |

Architect challenge: one transaction for the switch (board row, columns' limits, sprints, issue sprint
membership), concurrent issue moves during the switch, statement budget on big projects, the board
and backlog endpoints for each type, CLI/MCP contract (`board_type` in PATCH /api/projects/{key}
from SAN-225), export/restore already carry `board_type`.

## Decisions

Panel 2026-11-18 (one agent, product/ux/ia + architect notes), unanimous. Architect (orchestrator) adjustments marked A.

| # | Winner | Trade-off |
|---|---|---|
| 1 | (a) "Board type" sub-block in the General section (not the Danger zone: the switch is lossless and reversible) | looks less "serious" than Danger zone |
| 2 | (c) Scrum → Kanban keeps every sprint and each issue's sprint membership untouched; the Kanban board ignores sprints; switching back shows them exactly as before | sprint membership is invisible on Kanban |
| 3 | (b) closed sprints and reports kept, hidden with the Reports/Backlog nav (already gated on `board_type === 'scrum'`) until switched back | a report from a Kanban period needs a switch back |
| 4 | (a) Kanban → Scrum clears column limits and the done window, named in the confirmation | limits are not restored on a later switch back |
| 5 | (a) confirmation dialog listing what changes | one more click |

A1: no open-issue count in the dialog (it would need a new endpoint); the dialog uses what the page already has: number of sprints (Scrum → Kanban), number of column limits and the done-window days (Kanban → Scrum).
A2: `board_type` joins `PATCH /api/projects/{key}` (SAN-225) with an optional `expected_board_type` for the stale check (409 `board-type-changed`); one transaction under the existing project lock; no migration. CLI `santi projects edit --type scrum|kanban`; MCP `update_project` must pass `board_type` (today it is declared and dropped).
A3: an active sprint stays `active` while the project is Kanban; nothing auto-completes it; switching back to Scrum resumes it.
A4 (after qa): Scrum → Kanban sets the done window to the Kanban default (14 days) so a long-lived project's board does not load every done issue; the dialog says so.
A5 (after qa): Kanban → Scrum copy names only issues outside a sprint, since issues kept in a sprint from an earlier Scrum period return to it (A3).

## Copy (exact)

- Legend "Board type"; two options "Scrum" ("Sprints, a backlog and reports.") and "Kanban" ("One continuous board, no sprints."); the current one pressed; choosing the other opens the dialog.
- Scrum → Kanban dialog: title "Switch to Kanban?"; body "Open issues stay where they are and show on one continuous board.", "Done issues older than 14 days are hidden from the board." and, when there are sprints, "{n} sprint(s) and their reports stay as history, hidden until you switch back to Scrum."; buttons "Switch to Kanban" (primary), "Cancel".
- Kanban → Scrum dialog: title "Switch to Scrum?"; body "Open issues outside a sprint move to the backlog."; when limits exist "{n} column limit(s) are cleared."; when a done window is set "Hiding done work after {days} days turns off."; buttons "Switch to Scrum", "Cancel".
- Toasts "Switched to Kanban." / "Switched to Scrum.". Errors: 403 "Only a project admin can change the board type."; archived: existing archived message; 409 board-type-changed "The board type changed since you loaded this page. Reload to see the current type."; network "Couldn't switch. Try again." 

## States (ux)

- Idle: segmented control (two 44 px buttons, full width at 375, inline at 1440), current one `aria-pressed`. Admin only (section already hidden for members); archived: disabled with the existing locked treatment.
- Confirming: dialog (full-screen at 375), focus on the title, Esc/Cancel return focus to the option that opened it.
- Switching: primary shows "Switching…" with spinner, both buttons disabled, Esc ignored.
- Done: dialog closes, toast, control updates, Reports/Backlog nav appear or disappear at once (invalidate project queries), focus to the newly pressed option.
- Refused (409): dialog closes, inline error under the control (role=alert).

## Acceptance

- Switch both ways from web, CLI and MCP; nothing but the documented settings changes.
- Migration-free if possible; contract change → qa.
