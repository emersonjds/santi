# SAN-198 — Account security: change password and active sessions

SAN-93 slice 2. Today a person cannot change their own password (only operator reset links, migration 0023) and "Sign out" ends only the current session.

## Context

- Passwords: `check_password` (`crates/santi-server/src/auth/domain.rs:43`) asks for 10 to 128 characters; Argon2id hashes; `set_password_hash` and `delete_sessions` exist in `auth/repo.rs` (used by reset links).
- Sessions and API tokens share `auth_token` (`kind = 'session' | 'api'`, `created_at`, `expires_at` for sessions; no last use, no device). The session cookie is `__Host-santi_session`.
- Rate limits: `Action::Login (10, 6)`, `Action::Reauthenticate (5, 60)` in `rate_limit.rs`; delete account already asks for the password.
- `/account` (D54): one page — Profile, Preferences, API tokens, Your data. The panel for SAN-93 placed Security between Preferences and API tokens.

## Scope

- `POST /api/me/password { current, new }`: checks `current` (rate limited as Reauthenticate), applies `check_password` to `new`, refuses `new == current`, stores the new hash, ends every other session and keeps the caller's; API tokens are kept.
- `GET /api/me/sessions`, `DELETE /api/me/sessions/{id}`, `DELETE /api/me/sessions` (all but this one).
- `/account` Security section: change password form and the sessions list.
- CLI `santi password` (prompted twice, never an argument); no MCP tool.

## Decisions

Panel 2026-10-21: product, ia and ux; Q3 split, ia and ux win. Architect challenge (orchestrator), D60:
- Migration: `auth_token.last_used_at timestamptz` (set to `created_at` at creation) and `auth_token.client text` (at most 60 characters, sessions only).
- `client` is a label parsed from the User-Agent at sign-in by a pure function ("Chrome on macOS", "santi CLI", "Unknown device"); the raw User-Agent and the IP are never stored.
- `last_used_at` is refreshed by the session extractor only when it is older than 10 minutes (one UPDATE at most every 10 minutes per session; statement budgets unchanged for requests inside that window).
- `POST /api/me/password` answers `{ signed_out: n }`; it runs in one transaction (check, new hash, delete other sessions) and is rate limited as Reauthenticate per account and address. API tokens survive a password change (they are revoked from their own list).

| # | Question | Options | Winner |
|---|---|---|---|
| 1 | What a session row shows | (a) device label parsed at sign-in ("Chrome on macOS", never the raw user agent), signed in date, last active (updated at most every 10 minutes), "This device" badge, Sign out; (b) signed in date only and Sign out; (c) (a) plus the IP address |  (a), unanimous; no IP |

| 4 | Where Security sits and how it opens | (a) a section between Preferences and API tokens, form always visible; (b) same place, collapsed behind a "Change password" button; (c) its own route `/account/security` |  (a), unanimous |

## States (ux)

**Section.** `/account` keeps Profile → Preferences → Security → API tokens → Your data. Heading "Security"; two blocks: change password, then sessions.

**Password form** — fields: Current password (`autoComplete="current-password"`), New password (`autoComplete="new-password"`), Confirm new password (`autoComplete="new-password"`); all `PasswordInput` (independent show/hide per field). Hint under New: "10 to 128 characters." Submit "Change password"; saving shows the spinner and disables the button, label unchanged.
- Success: form clears, toast "Password changed. No other sessions were signed out." / "…1 other session was signed out." / "…N other sessions were signed out." (N = count returned by the API); focus stays on the Current password field for the next change.
- Errors (on the matching field, root otherwise): wrong current → "The current password is not right." on Current; too short/long → the 10–128 hint text on New; same as current → "Choose a password different from the current one." on New; confirm mismatch → "Passwords do not match." on Confirm; rate limited → root "Too many attempts. Try again in {N} minutes."; network/5xx → root "Could not change the password." with the submit button re-enabled so retry is just resubmitting.

**Sessions list** — loading: skeleton rows (same pattern as API tokens). Error: `LoadFailed` with retry. Empty (only this session exists): hide the "Sign out other sessions" button, show "Only this device is signed in." instead of a row list. Otherwise one row per session: device label ("Chrome on macOS"), "Signed in {date}", "Active {relative time}" (updates lazily, no live ticking), "This device" badge on the caller's own row with no Sign out button there; every other row has a "Sign out" button. Long device labels wrap, never truncate silently (no tooltip-only data). Many sessions: list scrolls inside the section, page itself does not grow unbounded.
- A "Sessions" subheading (h3) opens the list; "Sign out other sessions ({count})" sits below the list in both DOM and visual order, hidden when count is 0; no confirm dialog — signing back in costs one password entry, same cost as undoing a mis-click, so a modal would only add a click to the common case. Both bulk and per-row sign-out: row(s) removed on success, toast "Signed out {count} other session(s)." / "Signed out this session." respectively; error keeps the row(s) and shows a root error with retry.
- No permission (session API unreachable for this account type): section hidden, nothing shown in its place.

**375px** — sections stack full-width; password fields and sessions rows never scroll sideways; show/hide and Sign out buttons stay 44px; inputs render at 16px so iOS does not zoom.

**Dark theme** — reuses existing `Form`/`Input`/`Button` tokens, no section-specific colour.

**Keyboard & screen reader** — tab order: Current → New → Confirm → Change password → each session row's Sign out in list order → Sign out other sessions. Show/hide toggles are reachable between their field and the next field, each announces "Show/Hide password". Toast and inline errors use the existing `aria-live` region (`RootError`/`FormMessage`), read once on appearance. After a row's Sign out, focus moves to the next row's Sign out (or to the section heading if it was the last one) so the list never traps focus on a removed element.

## Acceptance

- Changing the password with the right current one ends every other session (their next request is 401) and keeps this one; the answer and the message give the count; a wrong current password, a rule failure, the same password and a mismatched confirmation each show their message and change nothing.
- The sessions list shows each session's device label, signed-in date and last activity, marks this device, signs out one session or all others; signing out this device is not offered there (the account menu does it).
- Neither the raw User-Agent nor any IP address is stored or returned.
- `santi password` prompts for the current and new password twice and prints the result.
- Gates: server (fmt, clippy, tests, sqlx check, perf budgets), web (typecheck, lint, format, coverage > 90 %, `/account` budget), qa adversarial review (auth), ux screenshots.
