# SAN-225 — Rename a project: name and key

Owner, 2026-10-29: renaming "Baixa Vídeo (BAIXA)" to "Nowvi (NOWVI)" took export → edit JSON →
restore → purge, losing issue history. The API has only GET and DELETE on `/api/projects/{key}` and
the CLI has no `projects edit`.

## Behaviour baseline (docs/specs/behavior/organizations.md)

- OR-37: keys are 2–10 characters, an upper-case letter first, then upper-case letters or digits;
  lower-case is rejected (not converted); a taken key is refused naming the project that holds it.
- OR-38: changing a key keeps the old ones as aliases: old links and issue keys still resolve, and an
  old key cannot be given to another project until it is removed from the previous-keys list. Only
  admins change keys. (santi today: "keys cannot change; no aliases".)

## Scope

- Project admins rename the project (name) and change its key, from the web (project settings), the
  CLI (`santi projects edit KEY --name … --key …`) and MCP (`update_project`).
- Changing the key renumbers nothing: issue numbers stay, only the prefix changes (BAIXA-3 → NOWVI-3).
- Old keys resolve: `/api/projects/{OLD}` and `/p/{OLD}/…` keep working (API answers for the
  project; the web redirects the URL to the new key); issue keys like OLD-3 in search, links, CLI and
  MCP resolve to NOWVI-3.
- A key held as an alias by project A cannot be taken by project B; A's admin can remove an alias
  (previous-keys list) to free it.
- History keeps the change (when SAN-186 lands; until then nothing to record).
- Data: `project_key_alias(key text primary key, project_id …)`, key uniqueness across live keys and
  aliases (one constraint/index strategy, the architect decides), migration.

## Open questions (panel)

| # | Question | Options |
|---|---|---|
| 1 | Where in the web | (a) project settings "General" section with Name and Key fields and Save; (b) a "Rename project" dialog from the project header menu; (c) both |
| 2 | Key change confirmation | (a) inline warning under the Key field ("Links with OLD keep working") and a confirm dialog on save; (b) just the inline note, no dialog |
| 3 | Previous keys | (a) a list under the Key field with "Remove" per alias; (b) hidden, removable only via CLI/API for now |
| 4 | Web URL with an old key | (a) client redirect to the new key preserving the rest of the path; (b) server 301 for `/p/OLD/…` |
| 5 | Naming | field labels, button text, success toast, error messages (taken key names the holder, invalid format) |

Architect challenge: one place that resolves a key (live or alias) for every route that takes
`{key}` (projects, boards, issues, imports, attachments, links, search, reports…) — not a patch per
handler; cost of the extra lookup (cache?), index for alias lookup, CLI/MCP issue-key parsing
(`OLD-3`), export/restore of aliases, the D-rule for "who can change keys" (project admin).

## Decisions

Panel 2026-11-18 (one agent, product/ux/ia lenses + architect notes). Architect (orchestrator) adjustments marked A.

| # | Winner | Trade-off |
|---|---|---|
| 1 | (a) "General" section in `/p/$key/settings`, above Board settings (unanimous) | one more click than a header dialog |
| 2 | (b) inline note under the Key field, no confirm dialog (unanimous; nothing is lost, old key stays an alias) | no second "are you sure" |
| 3 | (a) "Previous keys" list with Remove per alias (unanimous) | one more list to design |
| 4 | A1 overrides the panel's (b): the web redirects on the client. `GET /api/projects/{OLD}` answers for members with the canonical key; the router replaces `/p/OLD/…` with `/p/NEW/…` keeping the rest of the path. A server 301 would tell non-members a private project's new key. | a brief old URL before the swap |

A2: one key-resolution function, `projects::repo::resolve_project_key` (live key, else alias), used by the Member extractor's lookup (`members::repo::find_member_by_token`) and by every cross-project issue-key lookup (links, issues, restore). Clients (CLI, MCP) need no alias logic.
A3: data: `project_key_alias(key text PRIMARY KEY, project_id bigint NOT NULL REFERENCES project ON DELETE CASCADE, created_at timestamptz NOT NULL DEFAULT now())`. Live keys and aliases share one namespace: every write that assigns or aliases a key (create project, rename, restore) takes `pg_advisory_xact_lock(hashtext('project-key:' || key))` for the target key, then checks `project.key` and `project_key_alias`, then writes, in one transaction. Creating a project with a key held as an alias is refused too.
A4: `PATCH /api/projects/{key} { name?, key? }` (admin only, not on archived projects) and `DELETE /api/projects/{key}/aliases/{alias}` (admin). Renaming to one of the project's own aliases moves that alias back to live (the current key becomes an alias).
A5: export/restore carry the aliases.

## Copy (exact)

- Section "General". Labels "Project name", "Project key". Hint under Key (when focused or changed): "Links and issue keys with {CURRENT} keep working after you change it." Button "Save" (disabled until something changed; "Saving…" with spinner while saving).
- "Previous keys" list (only when there is at least one): each alias in the key chip style + "Remove".
- Toasts: "Saved." (name only); "Saved. {NEW} is now the project's key." (key changed); "Removed {OLD}. It's free for other projects now."
- Errors (on the Key field unless noted): "{KEY} is already {NAME}'s key."; "{KEY} is a previous key of {NAME}. Ask that project's admin to remove it before you can use it."; "Keys are 2 to 10 characters: a capital letter, then capital letters or digits."; "Only a project admin can change the name or key." (root); archived: the existing archived message; network/5xx: toast "Couldn't save. Try again." 

## States (ux)

- Non-admin: the General section is hidden. Archived: fields read-only, no Save, Remove disabled.
- Loading: its own skeleton; its own Suspense boundary (other sections render independently).
- Saving: fields and Save disabled. Error: inline under Key (role=alert, aria-describedby), focus to Key, typed values kept. Success: values update in place; a key change adds the old key on top of Previous keys and the URL moves to the new key.
- Many aliases: the list scrolls inside the section after ~6 rows; rows 44 px at 375.
- 375: stacked labels, full-width inputs (16 px), Remove right-aligned. 1440: the existing max-w-3xl column. Focus order: Name → Key → Save → Remove buttons. After removing an alias focus goes to the next Remove (or the section heading).

## Acceptance

- Rename name and key from web, CLI and MCP; issues keep numbers; old URLs, keys and links resolve.
- Alias blocks reuse until removed; removing frees it.
- Contract change + migration → qa review.
