# SAN-176 — Group invite link: one link with N spots

Owner (2026-10-19): team onboarding this week. The owner sends ONE invite link to a WhatsApp group
and up to N people join with it, each one recorded. Today an invite works once
(`members/domain.rs` `check_invite_usable`, `invite.used_at` set by `repo::take_invite`).

## Decisions

| # | Question | Winner |
|---|---|---|
| 1 | Data | `invite.max_uses` (int, default 1, check 1..=50) and a new table `invite_use` (invite_id FK cascade, user_id FK, used_at default now(), primary key (invite_id, user_id)). |
| 2 | Meaning of `invite.used_at` | Kept: it is set when the **last** spot is taken, so "full" and "used" stay one state and `check_invite_usable`, the preview and the 410 `invite-used` answer do not change. No backfill: old invites keep their `used_at`; nobody recorded who used them. |
| 3 | Accepting | One transaction: lock the live invite row (`FOR UPDATE`, active project, not expired, `used_at IS NULL`), add the member, insert the `invite_use`, and set `used_at = now()` when uses reach `max_uses`. Two people on the last spot: one joins, the other gets 410 `invite-used`. |
| 4 | Someone already in the project opens the link | 409 as today (member insert conflict), and the transaction rolls back: no spot taken. |
| 5 | Preview | `InvitePreview` gains `max_uses` and `spots_left`. |
| 6 | Create | `CreateInvite` gains optional `max_uses` (default 1); outside 1..=50 is 422 on `max_uses`. `Invite` (the create answer) gains `max_uses`. |
| 7 | Expiry | Stays 7 days (`INVITE_DAYS`). |
| 8 | Admin links (qa) | Only for one person: `role = admin` with `max_uses` > 1 is 422 on `max_uses`, "A link for more than one person can only add members."; the dialog checks the same before sending. |
| 9 | Rejoin with the same link (qa) | Blocked on purpose: someone who joined, then left or was removed, gets 409 `invite-already-used-by-you`, "You already joined with this link. Ask an admin for a new invite."; the transaction rolls back, no spot taken. The join page shows the server message. |
| 10 | Account erase and export (qa) | Erasing an account deletes its `invite_use` rows (accounts are soft-deleted, the cascade never fires); `invite_use (user_id)` is indexed. The export gains `invite_uses`: project key and `joined_at` of each link the person joined with. |
| 11 | Range copy (qa) | One message for an out-of-range number, server and web: "Between 1 and 50." `CreateInvite.max_uses` documents minimum 1 and maximum 50 in OpenAPI. |
| 12 | Network failure creating a link (qa) | The dialog stays open and shows "Could not create the link. Check your connection and try again." at the form root. |

## Web

- Invite dialog (`features/project/invite-dialog.tsx`): a "How many people" number field next to
  the role, 1–50, default 1, 16 px, 44 px targets; out of range shows "Between 1 and 50." under it.
- After creating: the link line says "Link for N people · valid 7 days" (N = 1: "Link for 1 person
  · valid 7 days").
- Join page: when `max_uses` > 1 it shows "N of M spots left" under what the invite grants.
- Full and expired links keep today's messages.

## CLI / MCP

- If an invite command or tool exists, it gets `--uses <n>` / `max_uses`. If none exists, nothing
  is added in this card.

## Acceptance

- A 3-spot link lets 3 different people join; the 4th gets the used answer; each join is one
  `invite_use` row.
- Two concurrent accepts on the last spot: exactly one joins.
- An existing member opening the link takes no spot.
- Existing single-use invites behave exactly as before.
- qa review (access control, concurrency, migration).
