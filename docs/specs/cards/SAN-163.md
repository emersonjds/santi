# SAN-163 — Import infers closed and active sprints

Found on PRM: Sprint 1 finished (all Done) and Sprint 2 running both came in as `future`. The export has no sprint state column and often no end date; `imports/domain.rs::closed_sprints` only closes a sprint when its issues rolled over or the row's end date is before today, and the importer never creates an `active` sprint.

## Rules (slice 1)

Sprints are ordered as today (order of first appearance / rollover order in the export).

1. **Closed** when the current rule says so (rolled over, or ended before today) **or** every issue whose last sprint is this one is in a done-category status.
2. **Active** (revised after qa, 2026-11-18): among the sprints that are not closed, the one whose export dates cover today (start <= today <= end); without dates, the **oldest** open sprint in chronological order. Chronological order: export dates when present, then rollover order (a row's sprint list goes older to newer), then natural order of names ("Sprint 2" before "Sprint 10"); row order of the file never decides. A sprint starting after today is future. At most one active sprint per board (D-rule). Dates: the export's start and end when present; otherwise starts at the import time and ends 14 days later.
2a. The preview suggests **future** instead of active when the target board already runs a sprint with another name; re-importing reuses a same-name sprint whatever its state (a future one is started when the plan says active).
2b. "Done" for these rules uses the category of the suggested status mapping (the same one the import applies), so localized status names behave like English ones.
3. **Future**: every other sprint.
4. Closed sprints keep only done work (existing rule); open issues of a closed sprint go where they go today.
5. A closed sprint gets its report facts as today (`record_sprint_facts`); the active sprint behaves exactly like one started by hand (board shows it, Complete sprint works).

## Contract

- `PlannedSprint` gains `state: "future" | "active" | "closed"` (replacing the `closed` boolean if nothing else needs it); OpenAPI regenerated, `web/openapi.json` committed, `pnpm gen:api`.
- The web preview (`features/import/mapping-step.tsx`) shows the inferred state as the default of each sprint's select (Future / Active / Closed / Skip), which also lets the user change it (orchestrator decision 2026-11-18: the select replaces the badge; a badge next to it would repeat the same word). At most one Active is allowed by the form. The CLI preview prints the state word per sprint.
- If the active sprint cannot be started at the end of the import (board started another sprint meanwhile, or the sprint ended with no issues), the import still succeeds and the result carries a problem row saying the sprint was left as future.

## Acceptance

- Unit tests in `imports/domain.rs` for: all-done last sprint → closed; newest sprint with open work → active; two sprints with open work → only the newest is active, the older one future (or closed if rolled over); kanban/no-sprint export unaffected.
- Integration test: importing the PRM shape (finished sprint + running sprint) leaves one closed sprint with a report and one active sprint on the board.
- Web: the preview shows the three badges (test); CLI preview prints the state.
