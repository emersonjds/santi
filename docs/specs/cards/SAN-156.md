# SAN-156 — Subtasks with their own workflow

Owner 2026-10-18: subtasks carry their own status and the parent follows them. Each subtask row in the issue view changes status (and assignee) in place, the parent shows a progress bar, and subtasks are created inline.

## Context

- `web/src/widgets/issue-detail/issue-subtasks.tsx`: lists subtasks (key, summary, read-only status pill) and creates one inline ("Add subtask", summary, Enter). No status or assignee change from the list, no progress.
- Board cards and backlog rows show `SubtaskCount` "open/total" (`web/src/entities/issue/issue-card.tsx:23`, D6).
- D6: moving a parent to done is silent, subtasks are flat cards in their own columns. D11: subtasks carry no points (SAN-149 leaves parity to the owner), so rows show no points.
- SB-22 (last open subtask done → offer to finish the parent) was left out by D6 and is reinstated by the parity rule (SAN-74).
- Status and assignee editing already exist in the issue fields (`issue-fields.tsx`: `StatusField` with `NativeSelect`, assignee field); moving an issue goes through the existing move/update API.

## Scope

- Subtask row: key, summary (opens the subtask), status control, priority glyph, assignee control. Changes save in place with the existing update/move endpoints; failure reverts with a fixed message.
- Progress on the parent: in the issue view's Subtasks header, and on the parent's board card and backlog row.
- SB-22: when the last open subtask reaches a done status (from the list or the board), offer to move the parent to done.
- No server changes expected beyond what the moves already do; the architect confirms.

Out: points on subtasks (D11, owner), reordering subtasks by drag, subtask type picker.

## Decisions

Panel 2026-10-21: product, ia and ux unanimous. Architect challenge (orchestrator): no server change; done = `total_subtasks - open_subtasks` from the existing `Card`, status and assignee go through the existing move and update endpoints. The chip now reads done/total everywhere, recorded as D57 (amends D6).

## States (ux)

**Subtasks header.** "Subtasks" alone when there are no subtasks (no bar, no count). With subtasks: "Subtasks · 2 of 5 done" above a thin bar (status-done token fill, track in the muted/border token); bar width is `done/total`, 0% is an empty track, not hidden.

**Row anatomy, 1440px.** One line: type glyph, key (tabular nums), summary (link, truncates, flex-1), status select (pill-styled, overlay `NativeSelect` per `RowPriority`'s pattern), priority glyph (overlay select), assignee avatar (overlay select, `RowAssignee` reused as-is). Long summary truncates with `title` for the full text; long key/status text never wraps the row.

**Row anatomy, 375px.** Two lines: line 1 — type glyph, key, summary (truncates); line 2 — status select, priority glyph, assignee avatar, each a 44px target per `HIT`. No sideways scroll; select text ≥16px so iOS does not zoom on focus.

**Status select.** `aria-label="Status of KEY-3"`. On change: optimistic, pill shows the new status immediately; a slim inline spinner replaces the pill while the move request is in flight. Failure: revert the pill to the prior status and show the toast "Could not change the status." (fixed message, no retry button — re-opening the select retries).

**Assignee.** Same control and copy contract as `RowAssignee`: `aria-label="Assignee of KEY-3"`, optimistic avatar swap, failure reverts the avatar and toasts "Could not change the assignee."

**Inline create.** Unchanged ("Add subtask" button → summary input, Enter submits, Escape cancels, error text under the input).

**SB-22.** Fires only when a status change makes the last open subtask done, whether the change came from this list or from the board — one toast per parent regardless of origin, and never a second one for the same parent change (e.g. two subtasks finishing in the same batch still yields one toast, debounced on the parent key). Toast: "All subtasks are done. Move PARENT-1 to Done?" with a Move button. Move sends the parent to the board's first done-category status. Success: "PARENT-1 moved to Done." Failure: "Could not move PARENT-1." (no retry button; Move is clickable again only via a fresh SB-22 trigger).

**Chip (board card, backlog row).** Shows "2/5" meaning done/total (changed from open/total, D6 addendum); `title="2 of 5 subtasks done"`. 0 subtasks: no chip, as today.

**Archived project.** Status select, priority select, assignee select and "Add subtask" all disabled (same as every other row field in a read-only project); no toast can fire because no change can start.

**Keyboard order.** Tab order per row: summary link → status select → priority select → assignee select; Enter on the summary link navigates, arrow keys inside an open native select cycle its options per browser default. Focus returns to the triggering control after any select closes (native browser behavior, not managed). The SB-22 toast's Move button joins the tab order only while the toast is visible and returns focus to the status select that triggered it once the toast closes.

## Acceptance

- In the issue view, each subtask row changes its status and assignee in place; a failure reverts and says so; the Subtasks header shows "N of M done" with a bar.
- Board cards and backlog rows show done/total with the title "N of M subtasks done".
- Moving the last open subtask to a done status, from the subtask list or the board, shows the SB-22 toast once; Move puts the parent in the board's first done status.
- 375 px: two-line rows, 44 px targets; archived projects show the rows read-only.
- Gates: web typecheck, lint, format, coverage > 90 %, size budgets; ux screenshot review at 1440 and 375, light and dark.
